# Contribution Rules

## Before Submitting a PR

### Security Checklist
- [ ] No credentials, tokens, passwords in code or comments
- [ ] No sensitive data (API keys, endpoints) committed
- [ ] GitHub token only in secrets (GH_PROVISIONING_TOKEN)
- [ ] `.env`, `.env.secret`, `.envrc` in `.gitignore`

### Code Quality
- [ ] Terraform code is valid (`terraform fmt`, `terraform validate`)
- [ ] Python code follows PEP 8 (`black`, `flake8` if available)
- [ ] No commented-out code blocks
- [ ] Variable names are clear and descriptive
- [ ] Changes align with existing code style

### Documentation
- [ ] README reflects any structural changes
- [ ] Workflow logic documented in PR description
- [ ] Risk classification rules updated if modified
- [ ] Architecture docs updated if design changes

### Testing & Validation
- [ ] Local validation: `cd infra && terraform plan -var-file=../repositories/example.tfvars`
- [ ] Terraform init succeeds: `terraform init -input=false`
- [ ] No terraform warnings or errors
- [ ] Risk classifier logic unchanged or rules updated
- [ ] Manual testing steps documented in PR

## PR Template Requirements

**Title:** Clear, concise (e.g., "feat: Add team module scaffold")

**Description:**
- What changed and why
- Risk tier (if applicable)
- How to test

**Type of change:**
- [ ] Bugfix
- [ ] Feature
- [ ] Refactoring
- [ ] Documentation

**Validation:**
- [ ] Terraform validates locally
- [ ] No secrets committed
- [ ] Code follows style guide
- [ ] Tests/validation documented

## Commit Guidelines

- **Concise messages:** "feat: X", "fix: Y", "docs: Z"
- **One logical change per commit**
- **Reference issues if applicable:** "Closes #123"
- **Attribution:** Co-authored-by for pair work

## Terraform Changes

### If modifying `infra/modules/repository/`:
- Test locally: `terraform plan`
- Document new variables in `variables.tf`
- Add outputs if needed
- Update README if behavior changes

### If modifying `infra/main.tf`:
- Validate module calls
- Check variable passing
- Test backend initialization

### If modifying risk classification in `scripts/classify_risk.py`:
- Document new rules in code comments
- Update `.ghdp/contracts/ARCHITECTURE.md`
- Test with sample terraform plans
- Consider impact on auto-merge logic

## Workflow Changes

### If modifying `.github/workflows/`:
- Document any new environment variables
- Ensure paths are correct (infra/, repositories/, scripts/)
- Test trigger conditions
- Update README if workflow purpose changes

## Code Review Expectations

- At least 1 approval required
- Security checklist must pass
- Terraform plan must be clean
- No merge conflicts

## Branch Naming

- Feature: `feature/short-description`
- Bugfix: `fix/issue-description`
- Ops: `ops/operation-type-resource` (auto-generated by workflow)
- Docs: `docs/subject`

## Merge Strategy

- Use squash merge for clean history
- Delete branch after merge
- Ensure CI/CD passes before merging
