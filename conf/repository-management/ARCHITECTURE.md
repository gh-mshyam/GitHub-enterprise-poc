# Repository Management System

Simple guide to how the system works.

---

## What This System Does

You edit a file called `repos.tfvars`. The system reads this file. Then it updates your GitHub repositories to match this file.

The system has one job: keep GitHub in sync with your code.

---

## How It Works

**Step 1:** You edit `infra/repos.tfvars`

**Step 2:** You commit and push to the develop branch

**Step 3:** A workflow creates a pull request automatically

**Step 4:** Another workflow checks what will change

**Step 5:** You review and merge the pull request

**Step 6:** The system applies the changes to GitHub

**Step 7:** Your repositories are updated

---

## The Three Things We Track

```
YOUR CODE
  repos.tfvars file
  ↓
WHAT TERRAFORM KNOWS
  terraform.tfstate file
  ↓
GITHUB REALITY
  Your actual repositories
```

All three must match. If they do not match, the system fixes them.

```

  Contains this documentation
```

## The Four Workflows

### 1. Import Workflow

**When:** You need to add an existing repository

**What it does:**
- You give it a repository ID
- It tells the system: "This repository already exists on GitHub"
- It gives you a template to add to repos.tfvars

**How long:** 10 seconds

**Who runs it:** You (manual)

---

### 2. Create PR Workflow

**When:** You push changes to the develop branch

**What it does:**
- Detects that you changed repos.tfvars
- Creates a pull request from develop to main automatically
- You can edit the pull request title and description

**How long:** 30 seconds

**Who runs it:** Automatic

---

### 3. Plan Workflow

**When:** A pull request is open

**What it does:**
- Checks your repos.tfvars for errors
- Shows you exactly what will change on GitHub
- Posts this information to your pull request

**How long:** 20 seconds

**Who runs it:** Automatic

---

### 4. Apply Workflow

**When:** You merge a pull request to main

**What it does:**
- Actually updates your GitHub repositories
- Adds new repositories if needed
- Updates existing repositories if they changed
- Archives repositories you removed

**How long:** 15 seconds

**Who runs it:** Automatic

## What Terraform State Is

The `terraform.tfstate` file remembers which repositories exist on GitHub.

Example state file:

```
Repository: api-server
  - ID: 123456
  - Visibility: private
  - Teams: backend-team, devops-team

Repository: web-app
  - ID: 789012
  - Visibility: private
  - Teams: frontend-team
```

**Important:** Do not edit this file by hand. The system manages it automatically.

## How Changes Work

### Scenario 1: Create a New Repository

**Your action:** Add new repo to repos.tfvars

**The system:**
1. Checks repos.tfvars for the new repo
2. Checks terraform.tfstate
3. Does not find the repo in state
4. Creates the repository on GitHub
5. Adds it to state

**Result:** New repository appears on GitHub

---

### Scenario 2: Import Existing Repository

**Your action:** Run the import workflow

**The system:**
1. Finds the repository on GitHub
2. Adds it to terraform.tfstate
3. Does NOT create a new repository

**Your next action:** Add the repository to repos.tfvars

**The system:**
1. Checks repos.tfvars (found)
2. Checks terraform.tfstate (found)
3. Updates the repository if needed

**Result:** Existing repository is now managed

---

### Scenario 3: Change Repository Settings

**Your action:** Edit repos.tfvars

Example: Add a team to the repository

**The system:**
1. Sees the change in repos.tfvars
2. Applies the change to GitHub
3. Updates terraform.tfstate

**Result:** Repository has the new team assigned

---

### Scenario 4: Delete a Repository

**Your action:** Remove repository from repos.tfvars

**The system:**
1. Sees the repository is no longer in repos.tfvars
2. Archives the repository on GitHub (soft delete)
3. Removes it from terraform.tfstate

**Result:** Repository is archived. Data is safe.

## What Each File Means

### repos.tfvars

This file defines all your repositories.

Example:

```hcl
repositories = {
  "api-server" = {
    name        = "api-server"
    visibility  = "private"
    description = "Core API service"
    teams       = ["backend-team"]
  }

  "web-app" = {
    name        = "web-app"
    visibility  = "private"
    description = "Customer portal"
    teams       = ["frontend-team"]
  }
}
```

**You edit this file.** The system reads it and updates GitHub.

### variables.tf

This file defines what fields repositories can have.

Example:

```hcl
variable "repositories" {
  type = map(object({
    name        = string
    visibility  = string
    description = optional(string)
    teams       = optional(list(string))
  }))
}
```

**You do not edit this file.** System developers maintain it.

### terraform.tfstate

This file stores what the system knows about GitHub.

Example:

```json
{
  "resources": [
    {
      "type": "github_repository",
      "name": "api-server",
      "id": "123456"
    }
  ]
}
```

**Never edit this file.** The system manages it automatically.

## Normal Workflow

This is how to make a change:

**Step 1: Edit repos.tfvars locally**

```bash
# Open in your editor
nano infra/repos.tfvars

# Add or change a repository
```

**Step 2: Commit your changes**

```bash
git add infra/repos.tfvars
git commit -m "Add new-api repository"
git push origin develop
```

**Step 3: Automatic pull request created**

You see a new PR automatically. It might say:

"chore: sync repos.tfvars (develop → main)"

**Step 4: System checks for errors**

The plan workflow runs. It shows:

"Planning to create: new-api repository"

**Step 5: Review and merge**

You review the plan. It looks correct. You merge the pull request.

**Step 6: Changes applied**

The apply workflow runs automatically. GitHub is updated.

**Step 7: Done**

New repository is created. System is in sync.

## Important Rules

### Rule 1: Always Use repos.tfvars

Always edit repos.tfvars. Never create repositories directly in GitHub.

✅ Correct:
```
Edit repos.tfvars → Commit → Merge → Update GitHub
```

❌ Wrong:
```
Create repo in GitHub UI directly
```

**Why:** The system does not know about direct creations. This breaks synchronization.

---

### Rule 2: Import Before Managing

If a repository already exists on GitHub, import it first.

✅ Correct:
```
Run import workflow → Get config → Add to repos.tfvars → Merge
```

❌ Wrong:
```
Add to repos.tfvars directly
```

**Why:** The system needs to know the repository already exists. Import tells it.

---

### Rule 3: Never Edit State File

Never edit terraform.tfstate by hand.

✅ Correct:
```
Let the system manage terraform.tfstate
```

❌ Wrong:
```
vim terraform.tfstate
```

**Why:** The system depends on this file being accurate. Hand edits break it.

---

### Rule 4: Use Git for All Changes

All changes must go through git commits and pull requests.

✅ Correct:
```
Local edit → git commit → git push → PR → Merge → Apply
```

❌ Wrong:
```
Terraform apply from local machine
```

**Why:** Git keeps an audit trail. Everyone can see what changed and why.

## Field Meanings

When you edit repos.tfvars, you use these fields:

| Field | Meaning | Example |
|-------|---------|---------|
| `name` | Repository name | "api-server" |
| `visibility` | private or internal | "private" |
| `description` | Shows on GitHub | "Core API service" |
| `has_issues` | Enable GitHub Issues | true |
| `has_wiki` | Enable GitHub Wiki | false |
| `teams` | Teams with access | ["backend-team"] |
| `topics` | Search tags | ["api", "go"] |
| `archive_on_destroy` | Archive when deleted | true |

## Troubleshooting

### Problem: "Repository already exists"

**What happened:** You added a repository to repos.tfvars but forgot to import it first.

**Fix:** Run the import workflow first. Then add to repos.tfvars.

---

### Problem: "Invalid syntax in repos.tfvars"

**What happened:** You have a typo or formatting error.

**Example wrong:**
```hcl
"api-server" {  # ← Missing =
```

**Example correct:**
```hcl
"api-server" = {  # ← Has =
```

**Fix:** Check your HCL syntax.

---

### Problem: "Workflow failed"

**What to do:**
1. Go to Actions tab
2. Click the failed workflow
3. Read the error message
4. Fix the error
5. Push again
